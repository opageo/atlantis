    Releasing

    Atlantis is released by pushing a git tag. The tag is the single source of truth for the version: there is no version number to edit in pyproject.toml, pixi.toml or the package.

    How versions work

    The package version is derived from git by hatch-vcs at build time:

    Checkout atlantis.__version__
    Exactly on tag v0.1.0 0.1.0
    On tag v0.2.0-rc1 0.2.0rc1 (pre-release)
    5 commits after v0.1.0 0.1.1.dev5+g<commit>
    No git history (e.g. tarball) 0.0.0 (fallback)

    Versions follow Semantic Versioning: while we are on 0.x, bump the minor version (v0.2.0) for new features or breaking changes and the patch version (v0.1.1) for fixes.

    Making a release

    Make sure everything for the release is merged into main and CI is green, then tag main and push the tag to the opageo repository:

    git switch main && git pull
git tag -a v0.1.0 -m "Atlantis v0.1.0"
git push git@github.com:opageo/atlantis.git v0.1.0

    The Release workflow then runs automatically. It:

    • builds the sdist and wheel with uv build;
    • checks the built version comes from the tag (no .dev versions);
    • installs the wheel in a clean environment and runs atlantis --help;
    • creates the GitHub Release with notes generated from the merged pull requests, and attaches the built files;
    • publishes to PyPI, if enabled (see PyPI).

    Zenodo then archives the GitHub Release and mints a DOI for it (see Zenodo). Finally, check the release notes on GitHub and edit them if needed.

    To try the process without making a real release, push a pre-release tag such as v0.1.0-rc1. It goes through the same steps and is marked as a pre-release on GitHub.

    If the workflow fails

    Fix the problem on main, then delete the tag and create it again on the new commit. If the GitHub Release was already created, delete it on GitHub first.

    git tag -d v0.1.0
git push git@github.com:opageo/atlantis.git :refs/tags/v0.1.0

    Never re-use a version number that has already been published to PyPI.

    Release notes

    Release notes are generated by GitHub from the titles of the pull requests merged since the previous tag, so clear PR titles make clear release notes. There is no separate changelog file.

    Zenodo (DOI)

    Each GitHub Release is archived on Zenodo, which mints a DOI for that version plus a concept DOI that always resolves to the latest version. Citation metadata (title, authors, license) is read from CITATION.cff.

    One-time setup (needed once per repository):

    1. Log in to Zenodo with GitHub.
    2. On GitHub, allow the Zenodo OAuth app to access the opageo organisation (Settings → Applications → Authorized OAuth Apps → Zenodo).
    3. In Zenodo, open Account → GitHub, click Sync now and enable opageo/atlantis.

    Only releases created after this switch is enabled are archived.

    PyPI

    Publishing to PyPI is disabled for now. To enable it:

    1. Agree on the PyPI distribution name (atlantis is taken) and set name in pyproject.toml. The import name and the atlantis command stay the same.
    2. On pypi.org, add a pending trusted publisher for the project: owner opageo, repository atlantis, workflow release.yml, environment pypi. No API token is needed.
    3. In the GitHub repository settings, create an environment named pypi and a repository variable PUBLISH_TO_PYPI set to true.

    The next tag pushed is then published to PyPI as well.

    Note: pip install needs the GDAL system library (version 3.13.0) because of the gdal dependency. Until that is addressed, the recommended install is pixi or uv from a clone of the repository.
